# AutoRia Tracker — специфікація

Щоденний моніторинг оголошень на auto.ria.com за збереженими пошуками:
що нового, що продано, що подешевшало.

## 1. Обсяг

- Джерело: **auto.ria.com** (лише вживані легкові, як у вибраних пошуках).
- Відстежуємо **збережені пошуки** з конфіг-файлу. Сумарно до ~300 активних оголошень.
- Користувач один. Фільтри редагуються вручну в `searches.yaml`.

## 2. Збір даних

**Спосіб:** звичайні HTTP-запити (без браузера, без проксі, без платного API).
Перевірено 2026-10-25 з домашнього IP:

- Сторінка пошуку `https://auto.ria.com/uk/search/?...` → `200`, у HTML є вбудований JSON
  з ID оголошень (`autoId`), цінами в USD і загальною кількістю (`count`).
- Сторінка оголошення `https://auto.ria.com/uk/auto___<id>.html` → `200`,
  містить повний `vin`, держномер, валюту продавця і статус (`isActive`). Деталі в `docs/recon.md`.

**Порядок запитів за запуск** (~20–50 запитів на день):

1. Для кожного пошуку пройти всі сторінки видачі, зібрати `id`, ціну в USD та базові поля
   (марка, модель, рік, пробіг, місто, URL).
2. Для **нових** ID відкрити сторінку оголошення й узяти VIN, держномер і дату публікації.
3. Для ID, які **зникли** з видачі, відкрити сторінку оголошення й визначити статус (див. §3).

**Ввічливість:** послідовні запити, затримка 1–3 с із джитером, реалістичний User-Agent,
до 3 ретраїв з backoff. При 403/429/капчі запуск переривається з помилкою, а не пише хибні дані.

**Адаптер джерела:** збір прихований за інтерфейсом `Source`
(`search(query) → ListingSummary[]`, `details(id) → ListingDetails`). Якщо HTML-підхід зламається
або IP GitHub Actions заблокують, на заміну є офіційний API (developers.ria.com, пакет 20k
запитів ≈ 420–500 грн).

**Ризик, який треба перевірити першим:** чи віддає сайт `200` на запити з IP GitHub Actions
(датацентр Azure). Якщо ні, є такі варіанти: self-hosted runner на Mac/VPS або API-адаптер.

## 3. Статуси та логіка змін

Кожне оголошення (`listing`, ключ — ID AutoRia) має статус:

| Статус | Коли |
|---|---|
| `active` | є у видачі хоча б одного пошуку |
| `sold` | зникло з видачі, а сторінка показує неактивне оголошення (`isActive=false`), 301 або 404. Сайт не розрізняє «продано» і «видалено», обидва рахуємо як продаж |
| `out_of_filter` | зникло з видачі, але оголошення ще активне (напр. ціна вийшла за межі фільтра). Не продаж, далі не відстежуємо. Якщо повернеться у видачу, знову `active` з тією ж історією |

**Події дня** (порівняння з попереднім успішним запуском):

- **Нове:** ID вперше в базі **і** його VIN/держномер не збігається з жодним відомим авто.
- **Репост:** новий ID, але VIN або держномер збігається з уже відомим авто. Новим не
  вважається, а приєднується до того ж `vehicle` (спільна історія цін і days-on-market).
  Попереднє оголошення закривається як `sold` **лише якщо** репосту за тим самим VIN немає.
- **Продано:** перехід `active → sold`.
- **Подешевшання:** будь-яке зниження ціни **у валюті, яку вказав продавець** (USD/UAH/EUR),
  відносно останнього спостереження. AutoRia перераховує ціни в інші валюти за поточним курсом,
  тож USD-ціна гривневого оголошення «плаває» щодня. Порівнювати її не можна, інакше будуть
  фальшиві зміни. Валюту продавця беремо зі сторінки оголошення, у дайджесті й дашборді
  показуємо також USD-еквівалент. Подорожчання записується в історію, але сповіщень про нього немає.

**Перший запуск** — це baseline: усе знайдене записується без подій «нове».

**Days-on-market** рахується від першої появи `vehicle` (з урахуванням репостів) до `sold`
або до сьогодні.

**Збій запуску:** якщо будь-який пошук не вдалося зібрати повністю, події «продано» для
нього не генеруються, щоб частковий збір не перетворився на масові хибні продажі.

## 4. Модель даних (SQLite, `data/autoria.db`, комітиться в репо)

- `searches(id, name, url, enabled)`
- `vehicles(id, vin, plate, first_seen_at)` — фізичне авто
- `listings(id /*autoria id*/, vehicle_id, url, brand, model, year, mileage_km, city,
  status, first_seen_at, last_seen_at, closed_at)`
- `listing_searches(listing_id, search_id)` — у видачі яких пошуків був
- `price_history(listing_id, observed_at, price_usd)` — рядок лише при зміні ціни
- `runs(id, started_at, finished_at, ok, requests, error)`
- `events(run_id, listing_id, type /*new|repost|sold|price_drop|out_of_filter|back*/, payload)`

## 5. Виводи

### 5.1 Telegram-дайджест
- Особистий чат, щодня ~**12:00 за Києвом**, надсилається **завжди**, навіть без змін
  (як ознака, що парсер живий).
- Зміст по кожному пошуку:
  - підсумок: `+N нових · −N продано · ↓N подешевшало · N активних`;
  - **нові** — марка/модель, рік, пробіг, ціна $, місто, посилання;
  - **подешевшання** — було → стало, −$ і −%, днів на ринку, посилання.
- Список проданих у дайджест **не входить** (лише лічильник).
- Якщо запуск упав, надсилається окреме повідомлення з помилкою і посиланням на лог Actions.
- Довгі повідомлення розбиваються на частини (ліміт Telegram 4096 символів).

### 5.2 Дашборд (статичний, GitHub Pages, публічний)
- **Таблиця активних** оголошень: фільтр за пошуком, маркою, моделлю, роком, ціною;
  сортування за ціною, пробігом, днями на ринку, датою; розкривна **історія цін** авто.
- **Days-on-market:** розподіл днів до продажу за моделями та ціновими діапазонами
  (на основі `sold`).
- Генерується з SQLite у JSON + статичний HTML під час кожного запуску.

### Поза обсягом
Google Sheets/CSV-експорт, графіки динаміки ринку, оцінка «вигідності» ціни,
багатокористувацький режим і керування через бота.

## 6. Інфраструктура

- **Стек:** TypeScript / Node 24 (`tsx`), вбудований `fetch`, парсинг вбудованого JSON
  `window.__PINIA__`, вбудований `node:sqlite` (без нативних залежностей), `yaml`; дашборд —
  статичний HTML + vanilla JS без збірки й CDN.
- **Репозиторій:** публічний.
- **Розклад:** GitHub Actions cron `0 9 * * *` (09:00 UTC = 12:00 Київ влітку / 11:00 взимку; GitHub
  cron не знає часових поясів, а запуск за розкладом може запізнюватися на 5–30 хв).
  Кроки: checkout → run → commit `data/autoria.db` → build & deploy Pages → Telegram.
  Також `workflow_dispatch` для ручного запуску.
- **Секрети:** `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`.
- Ріст БД: ~300 оголошень, історія лише змін. Мегабайти за роки, тож комітити в git ок.

## 7. Конфіг

```yaml
# searches.yaml
searches:
  - name: Camry 2017-2020 до $20k
    url: https://auto.ria.com/uk/search/?categories.main.id=1&brand.id[0]=79&...
```
Пошук задається URL'ом, скопійованим із сайту. Парсер сам дописує пагінацію.

## 8. Відкриті питання / перевірити під час реалізації

1. Відповідь сайту на запити з IP GitHub Actions (перший spike).
2. Точний маркер «продано» і вигляд видаленого оголошення (404, редирект чи банер).
3. Чи зберігає URL пошуку зі сторінки всі фільтри (сортування за датою, розмір сторінки).
4. Стабільність структури вбудованого JSON: парсер має падати голосно, а не мовчки
   повертати 0 оголошень (санітарна перевірка: `count > 0` і кількість ID ≈ `count`).
